# FR8029D BLE 链路长包与 SDK 外设服务兼容设计

目标是在裸机和 FreeRTOS 上支持 SDK v0.3.6 外设示例的双向 251 字节链路层数据长度协商和 FFF0 服务。两版继续支持现有 128 位 UUID 服务、1～20 字节写入、逐字节 Notify 回显以及 LE 1M、LE 2M。实施顺序为链路长包、SDK 服务。

## SDK 对照基线

同一台 Mac 的 SDK v0.3.6 HCI 记录中，默认连接的收发 PHY 都是 2M，Max TX Octets 和 Max RX Octets 都是 251，双方时间上限均为 2,120 µs。2026-11-26 重新连接 Flash 中的 SDK 镜像，发现 FFF0 下的 FFF3 和 0783B03E-8535-B5A0-7140-A304F4FF5CBA。FFF3 的首次读取为 00 01 02 03 04，订阅后收到 01 02 03 04 05；写入 00 至 13 共 20 字节后收到写确认，再读仍为 00 01 02 03 04。

## 一、双向链路长包

长包按固件构建选择，计划新增 Cargo 特性 `ble-gatt-dle`，默认关闭。裸机和 FreeRTOS 都可生成两种可烧录镜像：

| 烧录时选择的镜像 | 连接的数据长度 | 现有 Rust GATT 特征 |
| --- | --- | --- |
| 标准版（默认） | 沿用现有短包路径，链路层载荷上限 27 字节 | 单次写入和 Notify 回显 1～20 字节 |
| 长包版（启用 `ble-gatt-dle`） | 每次连接从 27 字节起步，按对端收发能力及时间分别协商，最高 251 字节 | 同上 |

两种镜像独立选择运行环境和 PHY；已有的 `ble-gatt-1m-only` 仍可固定 1M。FFF0/FFF3 服务兼容工作独立于长包开关。标准版在编译时排除长包专用代码和缓冲。验收时在相同构建参数下比较开关两侧的 Flash、静态 RAM 和栈水位，并将标准版与改动前的短包镜像对照。

现有 Rust 控制器的 LinkFrame 最多容纳 27 字节，HCI 编码暂存区为 64 字节。FR8029D 的 RX 描述符使用 260 字节的缓冲间距，但接收代码只复制最大 34 字节，当前无线事件时长也按短包计算。三个队列分别内联存放 8、16、8 个条目。将每个条目中的载荷扩大 224 字节，仅这三组队列的载荷存储就预计会多用约 7 KiB，实际大小取决于枚举布局及对齐。

- 每条新连接以对端 27 字节、328 微秒的参数起步。分别记录本地和对端的接收与发送字节数、时间上限，按方向求交集。支持双方发起的 LL_LENGTH_REQ 和 LL_LENGTH_RSP，处理同时发起、对端拒绝、重复请求和断开重连。仅在有效值改变时向 Host 上报 LE Data Length Change。
- 优先在 FR8029D 的 Packet RAM 中保留长包。队列保存受限的缓冲区索引、长度和连接代次。硬件接收缓冲必须在消费完成或将全部数据复制到已有所有者后才能归还。发送包直至 ACK 或连接终止才可回收，重传沿用原数据。用容量受限的静态缓冲管理长包，分别测量 Flash、静态 RAM 和最大观测栈深。
- 跟随协商上限调整无线事件预算，同时检查实际 PHY 可用的发送时间。验证 TX 数据区、RX 环、相邻描述符边界和硬件长度字段。只有接收和发送路径都就绪，才对对端声明支持长包。保留当前 Host 侧短 ACL 分片的兼容路径，验证长包的拆分和组装以及发送额度归还。
- 离线覆盖 27、28、250、251 字节边界、超限、非对称收发、时间限制、队列满和断开回收。实机用 SRAM 探针分别测试裸机和 FreeRTOS。先检查协商结果，再通过测试专用长数据交换，核对双向内容、板端描述符长度和完成状态。分开记录 HCI 协商和实际收发证据。现有 20 字节应用写入产生 27 字节链路载荷，单靠这条用例无法验证满长包。

协议依据见 [Bluetooth Core，Vol 6 Part B，Data Length Update procedure](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/low-energy-controller/link-layer-specification.html)。

## 二、SDK 外设服务

在现有 Rust 属性表末尾追加 SDK 示例的 FFF0 服务。原有服务、特征值和描述符的句柄应保持稳定。按 UUID 发现服务，结合新测试地址验证首次发现，另测已知设备重连。对于已有属性表缓存的客户端，单独检查重新发现策略。

| 客户端操作 | SDK 兼容接口的预期结果 |
| --- | --- |
| 读取 FFF3 | 返回 00 01 02 03 04，写入后再次读取也相同 |
| 对 FFF3 开启 Notify | 返回固定通知 01 02 03 04 05 |
| 对 FFF3 发出带响应写入 | 支持 SDK 的 20 字节上限，返回写确认 |
| 读取 FFF0 下的第二个只读特征值 | 使用 SDK 表内的 128 位 UUID 字节序，返回 11 22 33 44 55 |
| 读取用户描述符 | 按 SDK 返回对应特征的描述 |
| 订阅已有 Rust 特征值并写入 1～20 字节 | 只在该特征值上收到原样回显 |

CCCD 按连接和特征分别管理。测试两个特征各自订阅、同时订阅、取消订阅、断开后重订阅，核对通知归属。此轮范围为 FFF0 示例服务；配对绑定和 SDK 的 OTA 服务另行立项。

## 验收记录

两阶段分别保存裸机和 FreeRTOS 的构建、宿主测试、Mac 首次连接和重连日志、板端连接状态以及资源对比。硬件测试临时运行于 SRAM，结束后重新启动当前 SDK 固件并回读 Flash。若 Mac 仅提供长度协商事件，应据实标记实际 251 字节收发的验证状态。
