# device-content offline development record

Scope: only `crates/device-content/**`; no C source edits, device operations, staging, commits, new third-party packages, heap, RTOS or unsafe. This is an independent Rust 2024 workspace, not an automatically enabled root workspace member. `default = []`.

## Public codec bridge

- `descriptor(module: u8, key: u16, object: bool) -> Result<Descriptor, Error>` returns compiled schema metadata, not real backend capability.
- `decode_property(module, key, bytes, &Manifest) -> Result<Property<'_>, Error>` and `encode_property(Property, output, &Manifest)`.
- `decode_object(module, kind, bytes, &Manifest)` validates writes; `decode_object_read` tolerates future wallet provider numbers. `encode_object(Object, output, &Manifest)` validates readback. Text is exact UTF-8, u16 byte length, no NUL; extra/truncated fields fail.
- Property schemas: `07.P0001..0005` (phone); `08.P0001` (companion-radio, read-only in configuration catalog); `30.P0001..0003` (notifications); `31.P0001` (watchface). Additional `06.P0001` belongs to find and the built-in configuration route.
- Object schemas: `30.O0001` (notifications), `31.O0001` (watchface), `32.O0001` (weather), `34.O0001` (contacts), `35.O0001` (wallet), `36.O0001` (memo). The catalog test covers all 16 external routes.
- Shared `device-models::Notification` and `Weather` are reused. Only notifications selects models/notifications; only weather selects models/weather. Both path dependencies disable default features. phone/media/find/gimbal/companion-radio/contacts/memo/wallet/watchface do not pull either model feature implicitly.

`Manifest<'a>` fields are `string_max: Option<u16>`, `object_max: Option<u32>`, `property_max: Option<u16>`, `count_max: Option<u16>`, `heartbeat_timeout_s: Option<Range>`, `heartbeat_grace_s: Option<Range>`, `find_delay_s: Option<Range>`, `independent_call_bluetooth: bool`, `utc_ms: Option<TimeRange>`, and `watchface: Option<WatchfaceManifest<'a>>`. `Range` is inclusive u32 min/max; `TimeRange` is inclusive i64 milliseconds min/max.

`WatchfaceManifest` requires revision >0, actual nonzero logical width/height, supported dial/group/element/style ID slices, and `verified_resources: bool`. Missing required product parameters return Unavailable. Unknown IDs or out-of-canvas coordinates fail. Download state ready requires actual verified-resource selection. These fields must originate from trusted product/backend integration, never a phone's self-asserted authority.

Contact and memo layouts remain the frozen two-string and two-i64-plus-title layouts. Memo uses an explicit product calendar range and `start <= end`; no extra body/validity field is invented. Weather uses the existing strict F11 dictionary, ordered dates, canonical missing temperature fields and manifest day capacity. It makes no freshness claim.

## State-machine API and integration obligations

`Scope::new` accepts nonzero authenticated owner and connection incarnation from the session layer. `AccessPort::authorize` is a trusted port bound to the actual source phone. Packet fields are not credentials. All submit/settle operations recheck it; product integration must invalidate services on permission withdrawal or CCCD loss.

`ActionService<N>` (`MediaService` / `PhoneService`) reserves connection-scoped nonzero monotonically increasing u32 IDs. Ledger exhaustion and ID overflow fail closed, with no eviction/reuse inside a connection. `prepare` checks a real ActionPort, then `event_bytes` encodes a prepared outgoing event. `response_admitted` is called only after the complete response/event was accepted into the real transport queue; it invokes the backend once. Repeated admission returns recorded state. Prepared outgoing events cannot be serialized again after admission. Camera/music ACK values are frozen 0..3; SOS candidate result is 1..4. Known same-result ACK is idempotent, different result Conflict, unknown ID NotFound. Device music invokes only a real selected local player. Desired camera mode repeats are idempotent and never imply a photograph.

`invalidate` returns explicit IDs whose unconfirmed outcome is Unknown. No reconnect/reboot persistence or cross-connection exactly-once claim is made. `replace_scope` clears the old ledger; integration must publish/handle Unknown outcomes and never automatically replay them.

`FindService<N>` validates frozen target0 device/1 phone, pattern1..3, positive duration inside actual FindPort capability. Admission calls real start with deadline = external monotonic admission time + requested duration. Clock reversal and overflow fail. STOP prepares first; only its response-admission callback invokes stop. Timeout follows external monotonic polling and actual stop outcome. Receiving a result never implies found. Frozen C32 is 1 found/2 timeout/3 cancelled; candidate E81 is independently encoded 1 found/2 user-stop/3 timeout/4 backend-failure. E81 is available only for an actual terminal state. Invalidation marks unconfirmed work Unknown and attempts actual backend cleanup; cleanup failure is reported.

`NotificationService<'a,C,A>` registers typed committed content from the trusted source phone. Identical COMMIT retry does not alert twice; same notification updates without a new alert. Object IDs and notification IDs are distinct and conflicting mappings fail. Content presentation and call requests each have explicit response-admission callbacks. Incoming-call-only action bits are checked at registration, preparation and actual admission. Notification C30 has its own results1..5; it never shares camera's 0..3 dictionary. The dedup key is (notification, action), with immutable terminal results. DELETE, owner/connection replacement and CCCD invalidation clear pending work and its result ledger. Invalidation returns exact action tuples with explicit Unknown outcomes. UI/backend cleanup outside committed deletion remains the product session integration's responsibility.

`HeartbeatMonitor` echoes exact 4B tokens; tokens never authorize anything. Liveness uses external monotonic time, reports Waiting before the first actual heartbeat, Healthy only after one is received, then Grace/TimedOut at actual deadlines. Short output buffers do not refresh liveness. It performs no background hardware action.

`GimbalService<N>` covers 33.C34 and candidate E82 behind independent `gimbal`. Initiator action IDs are nonzero and monotonic per connection; exact same-ID retries return recorded state, changed parameters conflict, and ledger entries are never evicted for replay. Actual GimbalPort capability declares nonzero revision, supported mode/direction bits and duration-ms/angle-centidegree ranges. Missing backend returns Unavailable. `response_admitted` is the only submission point; BackendTicket must be nonzero and actually allocated by the backend. `poll` observes actual completion/failure/cancellation, then E82 encodes exactly action_id:u32,result:u8,reason:u16 (7B). Receiving a successful acceptance response never generates completion. Invalidation requests real cancellation and marks unconfirmed outcomes Unknown, including when cleanup fails. STOP action0 uses canonical direction0/mode0/value0 as an explicitly new candidate validation choice, not a claim about C firmware. Product range values are never invented.

`CompanionRadioService` covers 08.C30 behind `companion-radio`: exact one-byte bool, response-first real backend ticket, same desired state idempotent, reversal during Prepared/Switching is Conflict, actual P0001 readback confirms stable state. It never uses BLE state as Classic/audio readiness and never synthesizes a zero-state readback. P0001 readback is available only after actual port observation; the existing configuration layer can wrap changes in generic E90. Scope invalidation cancels pending real tickets and records Unknown without asserting physical radio shutdown. No source evidence for a selected backend means the product omits the feature.

Full endpoint scan of modules06/07/08/30..36 found no other module-specific command entries beyond the implemented FIND/STOP/RESULT, heartbeat/SOS result, radio switch, notification result, camera/music result/control and gimbal command. Object/configuration transport and persistence are delegated to their generic services.

## Contract authority and design choices

Read `CLAUDE.md`, `specs/application-protocol-development-design.md`, frozen `target/application-protocol-review/coverage-v05.json`, and `specs/protocol/v06-contract-proposal.json`. The 91 frozen contracts and core wire remain unchanged.

Unfrozen allocations follow the V06 candidate (platform1..3; phone status masks; notification category/action/result dictionaries; watchface metadata states; wallet provider0..17). One candidate correction was explicitly adjudicated by the parent task: E80 target uses the same frozen C30 values 0device/1phone, replacing proposal1phone/2watch. The same explicitly authorized candidate revision now adds the frozen C30 pattern byte to E80: ID:u32,target:u8,pattern:u8,duration_s:u16 = 8B. Pattern is exactly1 vibration/2 screen flash/3 both, never sound; unsupported actual phone patterns fail through its real backend. E80 was previously unfrozen, so this changes none of the 91 complete contracts or frozen C30. These are new design decisions, not claims about legacy C. All timeout/grace/delay/calendar ranges and supported watchface IDs/canvas come from manifest/backend parameters; none are guessed from source examples. Independent Classic status/address never derive from BLE.

## RED → GREEN and verification

Behavioral RED logs exist in target/: red-codecs.log, red-actions.log, red-find.log, red-notifications.log, red-phone.log, red-replay.log, red-replay-find-notifications.log, red-replay-notifications.log, red-withdrawn-permission.log, red-extra-routes.log, red-hardware-actions.log, red-gimbal-idempotence.log, red-find-pattern-v06.log. The recorded initial assertions failed because the corresponding behavior was missing. Additional boundary tests cover exact lengths, range/manifest failures, full ACK result sets, permission denial, admission/replay, scope invalidation, actual backend failure, deletion/owner cleanup, heartbeat and all 16 external catalog routes.

Run `python3 tools/verify.py` from this crate, or from any directory. It executes fmt, default + eleven single-feature + all-feature host tests, strict all-target Clippy, and Cortex-M0 checks; saves full command outputs under target/verification and a machine-readable verification.json. ARM verification is compilation/static analysis, not on-device execution. No production simulated backend exists; test ports live only in tests/.

Status: implementation frozen for independent review after the verification matrix; requested review fixes may reopen it. Integration/capability advertisement, transport admission, persistence and real hardware are separate layers and require their own evidence.

Keys exactly match the notification object's existing `source_app`, are nonempty/no-NUL validUTF-8 and strictly ascending by UTF-8 bytes.
